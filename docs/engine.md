# The engine: how the mod gets in, finds its way, and runs

Addresses are Steam build 10112070's (BH6.exe, base 0x400000, not relocatable); the mod finds every one of them by
name or signature at run time.

## The proxy and the boot

- BH6.exe is a plain PE: `.text` 0x401000+0x110002B, `.rdata` 0x1502000+0x235CAA (the import table at its start),
  `.data` 0x1738000+0x140B00 (only 0x88A00 of it in the file: the rest, the class records among it, zero-filled),
  `.rsrc`. No packer, no SteamStub; it imports `steam_api.dll` (on disk, Steam's) and `d3d9.dll` (Direct3DCreate9,
  D3DPERF_GetStatus, D3DPERF_SetOptions), `DINPUT8.dll` (DirectInput8Create); XInput is loaded at run time
  (`XINPUT1_3.dll`). The mouse in menus is read with GetCursorPos/ScreenToClient, and through DirectInput.
- The mod is `steam_api.dll`, in front of the game's own (renamed `steam_api_orig.dll`: 105,808 bytes, linked
  2012-08-28, 56 exports - 55 functions and the data export g_pSteamClientGameServer, forwarded in the .def). BH6.exe
  imports 17 of them. Every export is a `jmp [table]` thunk (`proxy.cpp`, list generated by `tools/gen_proxy.py`).
  Why this DLL: it is the one BH6.exe imports that ships with the game and that no common mod claims - ReShade and
  DXVK install as d3d9.dll, ASI loaders as dinput8.dll/version.dll/winmm.dll, controller wrappers as xinput1_3.dll -
  and it is not a Wine builtin, so Proton loads the app-local one with no override (d3d9 loads there too, as DXVK's
  is native, but that name is ReShade's; the others are builtins). The first build (a d3d9.dll, as RE5's) gave way to
  it on 2026-11-05. Steam's "Verify integrity" restores the game's steam_api.dll over the mod's and leaves
  steam_api_orig.dll: installing again is the fix (the message box says so when the original is missing).
- DllMain runs before the game's C runtime and static initializers; the exe's imports are bound by then (the loader
  binds a program's imports before running any DLL's DllMain), so DllMain re-points five of its import slots, found by
  name (`mem::iat_slot`), only when they hold a bound function: SetUnhandledExceptionFilter and ExitProcess (the crash
  logger), DirectInput8Create and GetAsyncKeyState (the input guard), and Direct3DCreate9 (`overlay_dx9.cpp`
  install_import: the mod's calls on to what the slot held - the system's d3d9.dll, or ReShade's or DXVK's in the
  game's folder, whose objects then get the hooks). These go in even when the program is not the game the mod knows
  (they are its imports, not its code); the discovery does not.
- An end the game's ExitProcess import never sees: abort() in the mod's own C runtime (ucrtbase - the game's is built
  in): an assertion, a C++ exception nobody caught. The runtime ends the process through its own ExitProcess, so the
  log's last line was `process exiting` with nothing about why (2026-11-06, ImGui's assert). The crash logger sets
  the runtime's SIGABRT handler at DllMain (`the game ends: abort() in the mod's C runtime ...`, with the stack), and
  ImGui is built with the mod's IM_ASSERT (`src/imconfig_re6cc.h`, the Makefile's IMGUI_USER_CONFIG): a failed check
  is logged once and ImGui recovers - the game goes on.
- The crash filter's chain (2026-11-10, found reading a crash report of RE4OGCabbyCodes', whose filter, chaining and
  once-a-second reassert this one shares). Two bugs, fixed:
  - SetUnhandledExceptionFilter made to do nothing - a crash handler keeping the slot for itself writes `ret 4` over
    its first bytes after setting its own (re4_tweaks' does, for RE4, with a CrashDumps folder beside the exe). A
    call then "returns" whatever eax held: each reassert took that (the tick's milliseconds since the last one,
    0x3E8..) for the previous filter, chained to it and logged "the top-level filter had been replaced (000003e8) -
    ours is back on top, chaining to it" every second. Now the API's first instruction is read, past the jumps in
    front (kernel32 into kernelbase, a hook's): a `ret`, or `xor eax,eax` and one, is said once ("crash:
    SetUnhandledExceptionFilter has been made to do nothing (a ret at ...)") and the mod stands aside - no reassert;
    install says "installed without its top-level filter" (and still takes abort); the game's call through the hook
    "did not go in". That handler reports a crash; this log has no CRASH line then. A "previous filter" that is not
    executable code is never chained to.
  - A filter set over the mod's that chains to the one it replaced - the mod's - which the reassert then chains to:
    a crash went round the two until the stack ran out (`tests/test_crash.cpp` against the build before: 6170 dumps,
    then the process died). Now each thread in the filter keeps the exceptions it is passing on (three deep): the
    same one handed back is stopped with one line ("back in our filter with the same exception ... not passed on
    again"); a new one, raised while the filter passed to runs (a packer's handler may raise one on purpose), is
    logged ("another exception, raised while ...") and passed on as any other, but not past three deep.
  - Also: the same exception given to the filter again is a line, not a second dump (nor a second memory log); each
    dump names the filter it is passed on to ("passed on to the filter at <module+0x..>") and has every register
    (ebx, esi, edi too) and the stack's top 0xC0 bytes raw (the faulting function's frame); a replacing filter's line
    names its module, once however often it puts itself back. Run offline (`tests/test_crash.cpp`, 26 checks); not
    seen at a real crash.
- The boot is the game's first Direct3DCreate9 (WinMain's renderer start-up): the class records exist by then.

## MT Framework 2's class records

- Each class's record (MtDTI) is a static object a static initializer builds: `push flagsB; push flagsA; push id;
  push size; push parent (0: the root); push name; mov ecx, record; call MtDTI::MtDTI (0xE67920); ... mov dword
  [record], record's own vtable`. 8344 such initializers, all of one shape.
- The record: +0 its own vtable, +4 name, +8 next sibling, +0xC first child, +0x10 parent (the root 0x179E660, which
  has no name, when none is given), +0x14 the next record in its id's hash bucket (256 buckets at 0x18145C8), +0x18
  size (bits 0..22) | flagsA << 23 | flagsB << 29, +0x1C id (the one given - an enemy's is its key, uEm1000 0x03100000,
  a player costume's 0x01xxxxxx - else crc32(name) & 0x7FFFFFFF). The children are appended to their parent's list as
  they are built, and the game sorts every list once it has started (0xE678E0 from sMain's start-up): MtObject is one
  of the root's children, not necessarily the first. Each is also appended to its id's chain (+0x14) in 256 hash
  buckets (0x18145C8, by the id's low byte): the game's lookup of a class by its key (0xE67750) walks them.
- Every class answers its record from vtable slot 4 (`mov eax, record; ret`), which gives its vtable: the mod indexes
  every 4-aligned `.rdata` dword equal to a getDTI function as a vtable's slot 4 - only where the five entries from
  there back (slots 0-4) are all code. Data can hold a getDTI's address by chance: zlib's fixed Huffman table (inflate's
  `lencode`, 0x17014A0, 512 entries {op, bits, val}) holds uEm6527's (0x890800) at 0x1701714 and 0x1701B14, and one
  more place holds cEm9900ActRide's (0x172F474) - 3 of 8816 hits, none a class's first. A hook is written only into a
  table that is a vtable up to its slot (every entry before it a function of the game's or one of the mod's hooks):
  the One hit kills builds of 2026-11-06 17:09-18:05 hooked "whatever function each class has" in slot 126 and wrote
  over entry 279 of zlib's table (it held 0xD10900, inside the code's range) - every archive inflated after came out
  broken and the game crashed loading (`docs/history.md`).
- The mod (`mt.cpp`) finds MtObject's record by its name's address in `.data`, checks the parent is a nameless record
  with it among its children, and walks the tree. The tools rebuild the tree from the initializers' arguments
  (`tools/mt_classes.py`); `tools/init_records.py` writes an image with the records filled in, for the offline test
  (their hash buckets too, since 2026-11-05: the game's own lookups by key run in the test's copy).
- Reflection: slot 3 is createProperty; each field is a stack record {name, type, owner, address} handed to
  MtPropertyList's new-node (0xE6E210) - `tools/mt_props.py` reads them. Types seen: 3 bool, 4 u8, 5 u16, 6 u32,
  9 s16, 10 s32, 12 float, 20 vector, 0x200000 an array.

## Systems, units, the tick and the pause

- Each singleton's constructor stores it in a global (`tools/globals.py`): sMain 0x186E1B4 (the sBioMain instance),
  sUnit 0x186E5F4, sPlayer 0x17D0468, sGameMan 0x17CF454, sInfoMan 0x17CF49C, sId (the UI) 0x17CF478, sQlocInput (the
  PC port's input) 0x17C1384, sCamera 0x186E23C, sSound 0x186E65C. The mod finds the systems through sBioMain's own
  fields instead (`game.cpp` survey_systems).
- sUnit: lines of 24 bytes from sUnit+0x3C (+0 flags - bit 1 the line off - , +4 the first unit), as many in use as
  sUnit+0x634 says, run in the order of the table at +0x48D4D4; a unit's state +0x10 (& 7: 1 starting, 2 running),
  next +0x18. Read out of sUnit's slot 10 (a line's walk) and slot 6 (its frame).
- A unit's coming and going (sUnit's slot 9, its line frame 0xF135A0): a starting unit (state 1) is made running (2)
  and started through its vtable's slot 5 (`mov eax, [edx+0x14]; mov ecx, esi; call eax` - no arguments;
  kSigUnitStart, the slot read out of the `mov`); a going one (state 4) is taken off its line, then destroyed through
  slot 0, its scalar deleting destructor, with 1 (kSigUnitDestroy). Both state words checked against the walk's
  (`units.cpp`; logged `started through slot 5, destroyed through slot 0`). The mod knows the enemies in play
  (`merc.cpp`: 191 vtables each) and the records' and skill screens (`records.cpp`) by those two slots, hooked -
  not by walking every unit each frame.
- **Hooks in vtables** (`vthook.h`, shared by `cheats.cpp`, `merc.cpp`, `records.cpp`): a slot of every vtable of the
  classes deriving from a base (or the base's own only), each table's original kept for the hook to call on to (by the
  object's vtable). A table is written only when it is a vtable that far: every entry up to the slot a function (the
  game's, or a hook of the mod's) - and its first five whatever the slot, as the class index asks: zlib's table, which
  holds uEm6527's getDTI twice, has a first entry (0x690800) inside the code and its second (0x290800) not, so a
  slot-0 hook asking only for the entries up to its slot would have taken it (2026-11-12; the index refuses it too).
  Unhooked only where a slot still holds the mod's hook (another tool's put in since is its).
- **The tick is an observer** (2026-11-12): it reads the pause, the characters (sPlayer's array: who is in play and who
  drives each), the mode and the match's step, and turns what changed into events - a switch turned, a character come
  into play, a match begun or ended. The cheats' own work is in hooks and re-pointed calls, where the game does the
  thing (`docs/cheats.md`, `docs/modes.md`); patches go in and out only as what they follow changes. Until then the
  tick wrote the health, the air, the ammo bit, the shots, the combo's earnings and the countdown hold each frame, and
  walked every unit for the enemies and the screens. What the panel shows (the inventories, the counters, the match's
  numbers) is read only while it can show (`game::Run::panel`: the pause, AlwaysShow, the panel up or asked for - set
  by `dispatch.cpp` after `game::tick`).
- The tick: sBioMain's vtable slot 6 (0x511D70), its frame, called by the main loop through the vtable on the main
  thread (only its destructor calls it directly). It checks Steam, runs sMain's own frame, then switches the pause,
  then either runs every system's update or, paused, the paused frame (0x511950) - which runs most of them, but not
  sLoadMan's (+0x10208): nothing loads while the game is paused unless the mod runs the loader's frame itself, after the
  game's (`dispatch.cpp`, for an Add's archive: `docs/inventory.md`, "The loader").
- **The pause**: sBioMain +0x104A9 is asked for (set by 0x511220 when Start is pressed in play - 0x9920E0, from the
  HUD's input check 0x993390; cleared by the paused frame when Start is pressed again after a cool-down, and by
  0x511240), +0x1049C is the state the frame switches to (and sUnit +0x48D6DE with it: the units stand still), +0x104A4
  the cool-down. While paused sId's frame runs a blink timer (+0x4598) and its paused draw dims the screen and blinks a
  "PAUSE" sprite, then draws the unit at sId+0x2C. The mod reads +0x1049C (kSigMainPause). Start is bit 0x8 of
  sQlocInput's pressed bits for the player's device (+0x3BC + 24 * device); on the keyboard it is the key the game's
  controls bind to Pause. Esc is another bit (0x2000, "back" in the PC port's key tables) and opens another menu, not
  this pause (seen in play 2026-11-05: no `screen: pause` with Esc; with the Pause key rebound, the panel at once).
- Threads: the main thread runs the loop and the tick; the hooks run where the game calls them (the damage in the
  units' update). The hooks read only the switches and the objects they are handed. What a hook shares with the tick
  is under a lock (the ammo bit's list, the dives logged, the enemies in play) or an interlocked word (Endless combo's
  banking).

## The memory log (`MemoryLog = <seconds>`, `memlog.cpp`)

- Why: the 2026-11-05 crash (`docs/history.md`) was DXVK out of memory in a 32-bit game. Proton Experimental runs a
  32-bit game in the old WoW64 (a 32-bit Linux process; the new one, `PROTON_USE_WOW64=1`, is forced only for two
  other app ids in its `proton` script): the game's 4 GB also holds the Linux side - Wine's 32-bit Unix libraries, the
  32-bit NVIDIA Vulkan driver (615.78.08: libGLX_nvidia -> libnvidia-glcore 30.5 MB -> libnvidia-gpucomp 149.8 MB,
  libnvidia-glvkspirv 14.2 MB, and gpucomp -> libnvidia-ptxjitcompiler 48.3 MB), its heaps, and the GPU memory DXVK
  maps in (`/dev/nvidia*`).
- The mappings: `\\?\unix\proc\<pid>\maps` (Wine's path to a Linux file; `Z:` the fallback). Not /proc/self: Wine's
  server opens the files a program asks for, so "self" is wineserver (30 mappings, all above 4 GB). The pid is
  found once: the process whose cmdline's argv[0] has this exe's name (Wine sets it to the Windows path) and whose
  list has this exe's image at its base. Kinds by path: anon (no path; no access = Wine's reserve for Windows),
  gpu (/dev/nvidia*, /dev/dri), nvidia libs, steam (ubuntu12_32, the overlay), wine (lib/wine, bin/wine), windows dlls
  (the prefix's drive_c/windows: DXVK's d3d9.dll is a copy there), game (its folder), shared (memfd, SysV, deleted),
  [heap], [stack], files (the rest). "Not mapped" is the Linux side's room (its mmaps take no reserved range); the
  Windows view (VirtualQuery) is the room of the game's and DXVK's own allocations. The room the marks go by: the
  smaller of the two (a 64-bit process: the Windows view's).
- Also: GetAvailableTextureMem from the present hook every 5 s; the mod's own heap (its operator new/delete and
  ImGui's allocator count each block's `_msize`).
- When: a line at start, every <seconds> (5 to 3600), at each `game started`/`game ended`; the whole list into
  `RE6CabbyCodes.maps.txt` (the run before's as `.maps.prev.txt`) at the first game, as the room falls under
  512/256/128/64 MB, and at a crash (the crash logger calls it).

## The frame log (`FrameLog = 1`, `framelog.cpp`)

- Why (2026-11-13): the user, "the game is still very laggy ... laggy when loading a save into the game and remains
  laggy while playing it" - after the cheats were made event-driven (the mod's own work a frame was already tiny).
  The log says where a frame's time goes, so the mod, the game and Direct3D can be told apart in one run.
- What: the main thread's frames (sBioMain's frame start to start, `dispatch.cpp`): the mod's tick, the game's frame
  function (a Present inside it taken out), the loader's after-frame; each Present split into the mod's part (the
  panel drawn there) and the device's own (DXVK taking the frame, and waiting when frames are ahead); the game's
  draw thread (its EndScene - the thread of the first one; the panel's scene on the main thread left out): its
  scenes and longest gap; the device calls that make something - textures (23, cube 25), vertex and index buffers
  (26, 27), vertex declarations (86), vertex and pixel shaders (91, 106): counted and timed, hooked only while the
  diagnostic is on (Wine: the device class's vtable with Present's; Windows: the adopted copy).
- A line a second (`frame: <the screen> | N frames in 1.00 s, N presents - average, the longest (over 33, over 100
  ms) | the game's frame | Present | the draw thread | the mod | made ...`), and a frame over 100 ms a line of its own
  as the next starts (`frame: a 164.0 ms frame (...) - the game's frame, Present, the mod, the rest`; 10 a second at
  most). Off, nothing is hooked or timed (each hook checks the switch).
- Reading it (2026-11-13's 10:40 run, `docs/history.md`): a long frame whose time is Present is the main thread
  waiting on DXVK - its command thread behind, compiling pipelines (in play); a long game's frame with thousands of
  shaders made that second is the game's shader creation waiting on DXVK's compile threads (at a load). Under Wine
  the game's draw thread (its EndScene) is not the main thread, and in some seconds no Present is made on the main
  thread at all (`Present 0.0` with 120 presents counted): the frames are still timed, start to start.
- The screen's name in the lines is a copy (`g_where`): the tick hands its own stack buffer, gone once the call
  returns (until 2026-11-13's fix the long-frame lines printed that dead buffer's bytes).

## Windows

- The adopt path (`adopt.cpp`): on Windows the D3D9 device and its swap chains get vtables of their own (the Steam
  overlay hooks what the classes' vtables point to). The game's window is the one whose class's window procedure is
  BH6.exe's own code (0xF35F70, registered with RegisterClassExW): RE5's check by class name had RE4's name in it and
  matched nothing.
- The window procedure is subclassed through the W entry point (CallWindowProcW converts for an ANSI one).
- Files beside the DLL are written whole and moved over (`files.h`: a virus scanner's lock is retried).
- BH6.exe has no ASLR (relocations stripped); the mod is relocatable and finds everything at run time.

## Proton: the game's movies (not the mod)

- RE6's pre-rendered movies are WMV (WMV3 1280x720, no sound track - the game plays the sound itself) in
  `nativePC/movie`: the logos (`re6logo`, `bh6logo` 17 s), the title backgrounds (`re6title`, `bh6title` 5 s), the
  cutscene movies `e5120` (75.6 s: Chris's event e2190 and Leon's e1210 show it - `data\event\e2190\e2190` names it)
  and `e5110` (30 s), and `projector` (50 s, 320x176: a projector screen in Ada's stage 1000, `s1000_mov_00`).
- Proton decodes no WMV. Its media converter (Proton's wine, `dlls/winegstreamer/media-converter/videoconv.c`) hashes
  the movie and plays Valve's Ogg Theora transcode of it from `steamapps/shadercache/221040/transcoded_video.foz`
  (Steam downloads it with the shader pre-cache). With none for that hash it plays a blank video, touches
  `placeholder-video-used` there, and dumps the movie into `fozmediav1/video.foz` for Valve.
- The hash is MurmurHash3 128 (seed 0x4AA61F63) of the first 48 MiB and then 8 MiB every 48 MiB. Its variant follows
  the game's unix side: x86 for a 32-bit one, x64 under WoW64. RE6 runs WoW64 here (`PROTON_USE_WOW64=1`, the user's
  launch option since 2026-11-05, for the memory room: `docs/history.md`). Valve's file of 2026-11-12 holds e5110 and
  the RE6 logo and title under both keys, but e5120, projector and the BH6 logo and title under the x86 key only. So
  e5120's cutscene played blank (2026-11-13).
- `tools/proton_videos.py` lists each movie's two keys and which the file holds; `--fix` adds the missing key as a
  second name for Valve's own transcode (the same header and data; a Fossilize database is read entry by entry to its
  end). It writes a new file beside the old one and moves it over, so a running game sees one or the other whole
  (the converter opens the file at each movie). `truncate -s <old size>` undoes it (the old file is the new one's
  start). Steam may download the file again; run the tool again then.
- RE5 is also 32-bit with WMV movies, and its shader cache (21690) has `placeholder-video-used` from 2026-10-29.
